The roof, the roof, the roof is on fire!

A short introduction to performance engineering

blog
Author

Jean-Christophe Loiseau

Published

September 29, 2026

We made it! We finally ended up with an implementation of Gauss-Seidel that solves our test problem (marginally) faster than Jacobi while also preserving its parallelization capabilities. Last time, we concluded this success with a parallelization study and the results looked somewhat similar to what is depicted in the left panel of the figure below. If we stop there, we may come up with the following conclusion: every time we double the number of threads, the solver computes the solution twice as fast. No doubt that, for this particular test case – a 512 \(\times\) 512 grid – it is effectively the case. If you don’t know any better, it may also be tempting to conclude that this scaling would hold true for larger grids. Or that, if I increase the number of points in each direction by 2 (so four times as many points), using four times as many threads would allow me to compute the solution in the same wallclock time. Pretty intuitive, right? But the right panel of this figure shows otherwise…

For the 512 \(\times\) 512 grid, the scaling is almost perfect. Every time we double the number of threads, we get a 2\(\times\) speed-up. But for the 2048 \(\times\) 2048 grid, almost all of the speed-up happens between one and two threads. Further doubling the number of threads does absolutely nothing, so clearly our intuition is wrong. But why? Is there a bug in our code, or have we simply slammed into a physical boundary of our hardware? This is what we’ll try to unravel in this post.

A simplistic model of the hardware

Processing units, whether CPU or GPU, are fantastic feats of modern technology. Just to give some intuition about how complex these can be, below is a block diagram of the AMD Bulldozer microprocessor.

Personally, I can’t really grasp all of the intricacies in this diagram. And mind you, this is a simplified representation, so I let you imagine how complex the true hardware can be! There is no way we can understand the different behaviour for the 512² and 2048² grids by tackling this level of hardware details head-on. We thus need to simplify things. And over-simplify we will.

Two resources: computation and memory

At a very, VERY high-level, CPUs can be understood as machines consuming two primary resources:

  • Compute: basically how fast the processor can run. It is typically measured in billions of floating point operations per second (Gflops/s).
  • Memory bandwidth: essentially how quickly data can be transferred through the memory hierarchy. It is typically measured in billions of bytes per second (GBytes/s).

In the rest of this post, we’ll actually consider two different types of memory, each with its own bandwidth:

  • DRAM (Dynamic Random-Access Memory): The main off-chip system memory that offers large storage capacity but exhibits high latency and limited bandwidth compared to on-chip caches.
  • L3 Cache: A fast, shared on-chip buffer designed to store frequently accessed data close to the CPU cores to minimize latency-heavy requests to main memory (DRAM).

With only these three elements, we arrive at the following (very) simplified block representation.

In the above diagram, \(P_{\max}\) denotes the maximum number of floating point operations per second the processor can do, while \(BW_{\text{DRAM}}\) and \(BW_{\text{L3}}\) denote the bandwidths of the DRAM and L3 cache, respectively. I’ll be the first to admit: it is a tremendously gross over-simplification of the (already simplified) diagram presented earlier. Yet, it is surprising how far this simplified model of the hardware can take us in the analysis of our kernels’ performance. But before showing you that, let us put some concrete numbers on \(P_{\max}\), \(BW_{\text{DRAM}}\) and \(BW_{\text{L3}}\).

Measuring the machine with likwid

We could trust the vendors and get these numbers from their datasheet. However, these are often slightly optimistic estimates, so we’ll actually use some well-defined benchmarks to get more realistic values. For that purpose, we’ll use likwid: a lightweight suite of command-line tools and a library designed for performance-oriented programming and hardware analysis on Linux systems. likwid stands for Like I Knew What I'm Doing. It is developed by the same group behind osaca, the open-source code analyzer we used here. I won’t get into the details of how to install likwid, nor how to use its different utilities. The documentation is rather comprehensive, and the team has uploaded a handful of tutorial-style videos online (here). So with that out of the way, let’s get to it.

Everything that follows is me using likwid to the best of my understanding. If I’m doing anything wrong or misinterpreting something, feel free to reach out. I’d love to stand corrected.

There is a lot to unpack here, and more than we actually need. The most important points are: it is an Intel TigerLake processor, with a single socket, 8 cores per socket, and up to 2 threads per core. Additionally, the L3 cache size is 24 MB, shared across all the threads. Moreover, since we can have two threads per core, we’ll use only every other thread to ensure 1 thread/core in the rest.

If you are familiar with Jacobi and performance engineering, you may already know why this 24 MB number is the key to our apparent mystery…

How to evaluate \(P_{\max}\)? To the raw performance now. We’ll use the likwid-bench utility, providing a large collection of standardized benchmarks to assess hardware performance. For peak performance, we’ll use peakflops_avx_fma. This kernel measures achievable (not marketed) peak double-precision throughput: it runs tight loops of independent, back-to-back FMA (fused multiply-add) instructions on a small working set (here, 32 kB) sized to stay resident in L1 cache. Since each FMA does 2 flops and the AVX2 FMA units on my CPU operate on 4 doubles at a time across two ports, this saturates the floating-point execution units and reports the sustained flops/s the core(s) can actually deliver. The estimate is typically somewhat below the vendor’s theoretical peak (turbo/clock throttling, instruction issue overhead, etc). Running it across thread counts gives the compute-scaling curve used to fix \(P_{\max}\) later on.

What about \(BW_{\text{DRAM}}\) and \(BW_{\text{L3}}\)? Again, we’ll use the likwid-bench utility, this time however with the triad benchmark. This kernel implements the classic STREAM Triad operation a[i] = b[i] + s*c[i], over a large array. Because the arrays are always freshly loaded from memory or cache and immediately used once (dropped, not reused), the memory system – not the floating point units (FPU) – is the bottleneck. The benchmark thus reports sustained achievable bandwidth. Which level of the hierarchy gets stressed is controlled purely by working-set size: a 1 GB working set can’t fit in any cache on this processor, so it exercises DRAM bandwidth. Alternatively, an 8 MB working set fits inside the 24 MB shared L3, so it exercises L3 bandwidth instead. Same kernel, same thread-scaling sweep, two different memory levels depending on that one parameter.

The figure above depicts the results of this hardware characterization experiment with an increasing number of threads being employed. Here are the most important take-aways:

  1. Compute scales (almost) linearly with threads; DRAM bandwidth basically doesn’t. Going from 1 to 8 threads roughly multiplies peak performance by 6.7 (from 76 Gflops/s to 484 Gflops/s), but DRAM bandwidth peaks at just 2 or 3 threads (~ 28 GBytes/s) and then decreases as more threads pile onto an already-saturated memory controller. A single thread already gets you most of the DRAM bandwidth this machine will ever offer.
  2. L3 bandwidth dwarfs DRAM bandwidth and shows no sign of saturating. At 8 threads, L3 delivers 416 GBytes/s against DRAM’s 23 GBytes/s – better than 15\(\times\) more – and it’s still climbing at N=8 rather than plateauing. This gap is precisely why a problem that fits in L3 can keep scaling with threads long after a DRAM-resident problem has hit a wall.
  3. Compute’s own scaling isn’t quite “ideal” either. The measured curve in panel (a) already sits visibly below the ideal linear reference by 8 threads. This is a reminder that \(P_{\max}\) itself softens as more cores turbo down together, so even the “good” resource isn’t a fixed constant once enough threads are in play.
We’ll see later that this decline doesn’t seem to carry over to the Jacobi/Gauss-Seidel kernels themselves

We now have all of the numbers we need to characterize the hardware. Let’s move on with trying to model the performance of our kernels and see how our model compares with actual computations.

From hardware to performance: the roofline model

We now have three numbers in hand: \(P_{\max}\), \(BW_{\text{DRAM}}\), and \(BW_{\text{L3}}\). But knowing your hardware’s ceilings doesn’t yet tell you how fast a given kernel should run. So let’s see how to do that.

The theoretical roofline

Arithmetic intensity. The one ingredient missing is a way to characterize the kernel itself. For that, define the arithmetic intensity of a kernel as

\[ \text{AI} = \dfrac{\text{flops}}{\text{bytes moved}}. \]

This is a property of the algorithm and its implementation, not of the hardware. A kernel that does a lot of arithmetic per byte it touches (high AI) can, in principle, keep the FPUs busy without waiting on memory. Conversely, a kernel that touches a lot of memory for very little arithmetic (low AI) will spend most of its time waiting on data, no matter how fast the processor is. Crucially, for a stencil kernel like Jacobi or Gauss-Seidel, both the flop count and the byte count per grid point are fixed by the discretization, so AI is a constant for the kernel. It does not depend on the grid size \(n\), only the sweep-level cost does.

Resource allocation as a linear program. Here’s the idea. Rather than asking what does the roofline plot look like, let’s ask a more direct question: given our three hardware ceilings and a kernel’s arithmetic intensity, what is the best throughput we could possibly hope for? That’s an optimization problem, and a particularly simple one: a linear program.

Since we’ve been measuring everything in sweeps over the whole grid since the very first post, let’s keep using that unit rather than switching to raw Gflops/s. If \(f(n)\) denotes the number of flops per sweep for a grid of size \(n\), then \(S = P/f(n)\) converts a flop rate \(P\) into sweeps per second. This is just a rescaling of the flop-based problem by the constant \(1/f(n)\), so it doesn’t change which constraint ends up binding. It just expresses the answer in units we already care about.

The resulting linear program reads

\[ \begin{aligned} \mathrm{maximize} & \quad S \\ \mathrm{subject~to} & \quad S \cdot f(n) \leq P_{\max} \\ & \quad S \cdot f(n) \leq BW_{\text{DRAM}} \times AI. \end{aligned} \]

The first constraint says: no matter what, you can’t sweep faster than the processor can compute. The second says: no matter what, you can’t sweep faster than data can be fed to it from DRAM. This simplified model thus gives us an upper bound on the attainable throughput: whichever constraint is tighter is the active roof, exactly the \(\min\) that gives the roofline its characteristic bent shape.

Accounting for L3. The same reasoning that gave us the DRAM constraint applies to any level of the memory hierarchy a kernel’s working set happens to reside in – but not by adding a second, simultaneous bandwidth constraint. If the working set fits inside the 24 MB L3 cache, DRAM traffic becomes a one-off cost that gets amortized away over the many sweeps required by the solver to converge, so DRAM bandwidth simply isn’t part of the story for that grid size. Conversely, once the working set spills out of L3, every sweep pays the full cost of moving data from DRAM, and L3 residency isn’t happening at all. The two ceilings are mutually exclusive regimes, selected by problem size – not competitors in the same constraint.

This means we don’t need to change the structure of the LP at all: we only need to let the bandwidth ceiling itself depend on \(n\),

\[ BW(n) = \begin{cases} BW_{\text{L3}} & \text{if the working set fits in L3}, \\ BW_{\text{DRAM}} & \text{otherwise}, \end{cases} \]

giving the final LP formulation

\[ \begin{aligned} \mathrm{maximize} & \quad S \\ \mathrm{subject~to} & \quad S \cdot f(n) \leq P_{\max} \\ & \quad S \cdot f(n) \leq BW(n) \times AI \end{aligned} \] Rather than treating “L3-resident” and “DRAM-resident” as two separate stories requiring two separate analyses, they’re now a single feasible region whose second constraint simply looks up the right ceiling for the grid size at hand. Which constraint binds – compute, or whichever memory level is relevant – depends entirely on where your problem happens to sit, through \(n\)’s effect on \(f(n)\) and the working-set size. This is what will let a single model account for both panels of the very first figure in this post.

This now becomes a parametric LP. Nothing actually prevents us from further parameterizing \(P_\max\) and \(BW(n)\) as a function of the number of threads as well.

A subtlety: the roof moves with the problem size

If you’ve come across a roofline plot before, you’ve probably seen it used to compare several different kernels or algorithms, each sitting at its own arithmetic intensity, against a single fixed roof. Our situation is a little different, and worth walking through carefully: since \(AI\) here is a property of the kernel alone, it doesn’t move as the grid size \(n\) changes – your kernel sits at the exact same horizontal position on the plot no matter how big a problem you throw at it. What changes with \(n\) is which roof is above that point.

Picture two roofline curves drawn on the same axes, sharing the same flat compute ceiling \(P_{\max}\) but with two different sections: a higher sloped section governed by \(BW_{\text{L3}}\), and a lower one governed by \(BW_{\text{DRAM}}\). Because \(BW_{\text{L3}} \gg BW_{\text{DRAM}}\), the L3 roof’s ridge point sits much further to the left than the DRAM roof’s – meaning it takes a much lower \(AI\) to be compute-bound under it. Jacobi and Gauss-Seidel are stencil kernels with a handful of flops per grid point against several bytes of neighbor data, which puts them at fairly low arithmetic intensity – plausibly low enough to sit on the sloped part of both roofs, not just the DRAM one. If that holds up once we compute the actual numbers in the next section, the real story isn’t “compute-bound at small \(n\), memory-bound at large \(n\)” – it’s memory-bound throughout, just against two very different bandwidths. Either way, the mechanism is the same: nothing about the kernel changes as \(n\) grows, but the ground shifts underneath it once the working set spills out of L3, and it’s this shift – from one sloped ceiling to a much lower one – that produces the two panels in this post’s opening figure.

So, what about Jacobi and Gauss-Seidel then?

Now that we know what the roofline model is, the only missing pieces of information are the arithmetic intensities of both kernels. So let’s start with that.

Our kernels have low AI.

As stated before, the arithmetic intensity (AI) is the ratio of the number of flops divided by the number of bytes moved from memory to actually perform these operations. It is important to note that this is for updating a single grid point. So let’s look at the two update rules again and start counting.

Jacobi kernel. The update rule reads

u(i, j) = 0.25_dp * (b(i, j)*dx2 + v(i-1, j) + v(i+1, j) &
                                 + v(i, j-1) + v(i, j+1))

Let’s begin with the number of arithmetic operations because this is the easiest. We have 4 additions and 2 multiplications. So a grand total of 6 flops for a single grid point update.

Let’s move on with the number of bytes moved. These include both bytes fetch from memory (the right-hand side) and written to memory (storing the updated value). Naïve accounting would suggest:

  • 5 double-precision floating point numbers need to be fetched from memory (b(i, j), v(i+1, j), v(i-1, j), v(i, j+1) and v(i, j-1)).
  • 1 double-precision floating point number needs to be written to memory (u(i, j)).

So that is a total of 6 double-precision floating point numbers, corresponding to 48 bytes per grid point. It is important to emphasize however that these 48 bytes are a strict upper bound that applies only in the worst case scenario, i.e. if every time we touch the values in u, b or v, they need to be fetched from memory. But compilers are smart. Not every reference to v, b, or u is a genuine trip to memory. Within a single sweep, v(i, j) gets referenced as a neighbor by up to 4 different point updates. If it’s still resident in cache from a few iterations ago (true here, since the sweep only needs 2–3 rows in flight at once), only the first of those references pays the memory cost; the rest are served from cache for free. On the other hand, the best scenario is every value is only fetched once from memory. That would give us 3 double-precision floating points numbers (u(i, j), b(i, j) and v(i, j)) per update, for a grand total of 24 bytes. The actual truth is somewhere in between these two extremes, but we’ll go for the 24 bytes as, for these simple kernels, it is probably much more realistic.

It is now time to do some elementary school mathematics. For the Jacobi kernel, the arithmetic intensity is

\[ \text{AI} = \dfrac{6~\text{flops}}{24~\text{bytes moved}} = 0.25 \]

Not a very big number if you ask me, but it is what it is. It basically means that, for every arithmetic operation the kernel does, it needs to read or write 4 bytes from memory. For reference, had we considered the pessimistic upper bound, we would get an arithmetic intensity of 0.125 (so 8 bytes needed for every arithmetic operation).

Gauss-Seidel. Time to move on with the Gauss-Seidel kernel

u(i, j) = 0.25_dp * (b(i, j)*dx2 + u(i+1, j) + u(i-1, j) &
                                 + u(i, j+1) + u(i, j-1))

As far as flops go, the story is exactly the same: 4 additions and 2 multiplications, for a grand total of 6 flops. And it is the same for the memory traffic. Even though Gauss-Seidel uses only two buffers, it still needs to at least read the two arrays b and u, and to write the updated array u once. For the pessimistic case though, the bytes count is 48 bytes (5 loads and 1 write). And for the optimistic case, same as Jacobi again: 24 bytes (2 loads and 1 write). This leads to a lower bound of 24 bytes per grid point per sweep. Again, the actual truth is in-between, but we’ll use the optimistic bound again. This gives us the arithmetic intensity

\[ \text{AI} = \dfrac{6~\text{flops}}{24~\text{bytes}} = 0.25, \]

the same as Jacobi.

How much work is a sweep? For a standard roofline analysis, we could stop right there and proceed with the analysis itself. But because we’ve characterized everything so far in this series in terms of number of sweeps per second rather than raw Gflops/s, we need to account for that. This is precisely what the function \(f(n)\) introduced earlier does. It is the number of flops per sweep, and it is the same for both Jacobi and Gauss-Seidel. Since \(n\) is the number of points per direction (including the boundary ones), and both kernels require 6 flops per grid point, the total number of flops per sweep thus is

\[ f(n) = 6 \cdot (n-2)^2. \]

For our two test grids, this works out to \(f(512)\) = 1 560 600 flops/sweep, and \(f(2048)\) = 25 116 696 flops/sweep. This is roughly the 16\(\times\) jump you’d expect when quadrupling the resolution along each direction (so 16 times as many points).

Roofline analysis predicts memory bandwidth is the binding constraint.

Alright, let’s move on with predicting the number of sweeps per second for each kernel. Note that we don’t actually need a solver for the linear program. You can easily convince yourself that the solution is given by

\[ S = \min \left( \dfrac{P_\max}{f(n)}, \dfrac{BW(n) \times AI}{f(n)} \right). \]

Modulo the \(1 / f(n)\) scaling to transform Gflops/s into sweeps/s, this is exactly the expression you’d find if you look up roofline analysis on the internet. So let’s put some numbers in. We’ll assume for now that we use all 8 threads so that the likwid estimates for \(P_{\max}\) and \(BW(n)\) are

  • \(P_\max = 483\) Gflops/s
  • \(BW(n) = 417\) Gbytes/s if the problem fits entirely in the L3 cache, or \(BW(n) = 28.5\) Gbytes/s otherwise.

Plugging-in the expression for \(f(n)\) and the arithmetic intensities of the two kernels, we get the following for the 2048² grid.

Kernel Maximum number of sweeps per second
Jacobi 279
Gauss-Seidel 279

Let’s use the actual roofline plot to make sense of these.

The two kernels sit very comfortably along the slanted line, corresponding to the memory-bound region. For the 2048² grid, DRAM bandwidth is thus the limiting factor here for both. The picture would have essentially been the same had we consider the 512², with the DRAM bandwidth simply replaced by that of the L3 cache. But are these predictions any good?

Let’s put that to the test.

Do the predictions match the effective number of sweeps/s measured numerically?

Let us consider only the 2048² case for now. The experimental setup is as follows: both kernels are compiled with gfortran -O3 -mtune=native -march=native -fopenmp -ftree-loop-vectorize=8 to enable vectorization and full multithreading over the 8 physical cores of my laptop. We run both kernels 10 000 times, measure how long it takes, and extract the number of sweeps per second. Simple enough, right? So here are the results.

Kernel Predicted number of sweeps per second Measured number of sweeps per second
Jacobi 279 272
Gauss-Seidel 279 219

And look at those numbers for Jacobi! The model predicts 279 sweeps per second, the actual experiment reports 272. Despite how simple our model is, it nails it. But the agreement for Gauss-Seidel ain’t that good though. We’re off by 20% or so. So what is going on here?

To partially explain this observation, we need to go back to the full kernel. So here it is.

do k = 0, 1
    do j = 2, n-1
        istart = 2 + mod(k+j, 2)
        do i = istart, n-1, 2
            u(i, j) = 0.25_dp * (b(i, j)*dx2 + u(i+1, j) + u(i-1, j) &
                                             + u(i, j+1) + u(i, j-1))
        end do
    end do
end do

See what’s happening here? We’re looping over the whole arrays twice, but that is not the issue. What really matters is that we read and write only every other point. I’m not an expert on CPU but, apparently, when a CPU writes to a cache line that isn’t already resident, it normally has to first read the full 64-byte line from memory before it can modify the 8 bytes you actually wanted to change. It can’t write a partial line without knowing what the rest of it contains. This is the write-allocate / read-for-ownership cost (RFO), and it’s a real, extra 8 bytes on top of the write itself. So the effective number of bytes moved is not 24 but 32. And consequently, the corresponding arithmetic intensity decreases from 0.25 (our initial estimate) down to 0.1875 – worse than Jacobi. If you redo the math with this new AI, you would find a theoretical maximum of 209 sweeps per second so… our model nailed it again (after we’ve accounted for the read-for-ownership extra bytes)!

Is this the whole story? I don’t know, but it certainly seems like a very plausible explanation.

Extending our model to include the number of threads

So our model works remarkably well for the 8 threads computations and predicts that, for the 2048² grid, both kernels are memory-bound. But does it correctly predict the number of sweeps per second if we keep the grid constant but vary the number of threads used from 1 to 8? Let’s find out! The only modification we need to make is that the peak performance \(P_{\max}\) and bandwidths \(BW\) now depend on the number \(T\) of threads. So here are the results.

Plugging in the measured Triad bandwidth curve directly here (which declines past 2-3 threads, as we saw earlier) makes the model under-predict at high thread counts. Measured throughput ends up exceeding the predicted ceiling by up to 25%, which shouldn’t happen for what’s meant to be an upper bound. Holding DRAM bandwidth flat at roughly its 2-3-thread peak (~28.5 GBytes/s) instead of letting it decline fixes this for both kernels at once, which is a stronger signal than it might look: it suggests the standalone Triad benchmark’s falling bandwidth at 6-8 threads isn’t representative of what these stencil kernels actually sustain. One possible explanation is that Triad’s back-to-back streaming loads leave the memory controller no compute-induced gaps to work with, unlike a kernel doing 6 flops of dependent arithmetic per point. The rigorous way to settle this would be measuring DRAM traffic directly during the Jacobi/GS runs themselves (e.g. with likwid-perfctr’s memory group) rather than borrowing the number from Triad – on the list for a follow-up.

And there you have it! It looks very much like the very first figure in this post, but now we can come up with an explanation. The two kernels are memory-bound for both grid resolutions. For the smaller grid though, all the data fit comfortably inside the L3 cache. As a consequence, the almost linear speed-up observed as we crank up the number of threads is directly related to the increasing L3 bandwidth obtained with increasing threads count already observed when benchmarking the hardware with likwid. To be completely honest, this holds up well for Jacobi throughout, but the fit for Gauss-Seidel visibly worsens as thread count grows. The predicted and measured sweep rates diverge by close to 50% at 7-8 threads, suggesting the simple read-for-ownership correction that worked so well for the DRAM-bound case does not transfer cleanly to the L3-bound regime. Very likely, the details of L3 traffic are more complicated than what can be accounted for with our ridiculously simple model. Nonetheless, the predictions are still in the correct ballpark, which is good enough in my opinion given how simple our model is.

For the larger grid, the working set no longer fits in L3, so DRAM becomes the dominant memory level. But again, the jump observed when moving from 1 to 2 threads can be entirely explained by the increase in DRAM bandwidth reported with likwid. For larger thread counts, this DRAM bandwidth however saturates. And since the two kernels are memory-bound anyway, the increased peak performance observed for increased thread counts cannot kick in. The number of sweeps per second thus saturates also to roughly 270 sweeps/s for Jacobi and 210 sweeps/s for the red/black Gauss-Seidel kernel. Mystery solved.

Where does that leave us?

I told you: oversimplify we will, and oversimply we have! I’ll be the first to admit: our model of the hardware is ridiculously simple. Yet, I am still amazed at how good its predictions are (most notably for the larger grid size). The main take-away however is that both kernels run essentially as fast as they possibly can on my hardware. So, have we finally reached the end of the road?

Well… not quite yet. But we’re getting there, trust me (I’m a Doctor). Going back to Gflops/s, Gauss-Seidel and Jacobi achieve something like 5 and 7 Gflops/s on my laptop. This is 70 to 90 times less than what my CPU can deliver. That is an enormous amount of idle compute capacity just sitting there, unused precisely because we’re memory-bound. The next lever for increased performance isn’t however the one people usually reach for first. The instinct here is often “try loop tiling,” but ordinary spatial tiling can’t fundamentally help: it works by improving cache reuse within a sweep, but we already achieve near-ideal reuse for Jacobi. There’s no further reuse to extract from a single pass over the grid. For Gauss-Seidel, measured throughput is likely close to its floor too, but the read-for-ownership story suggests there may be a few percent left on the table from smarter store handling (outside the scope of what a bytes-moved model alone can settle). The opening isn’t spatial, it’s temporal. But we won’t be going down this road, so look for diamond tiling, trapezoidal decompositions, and wavefront schedules if you want to know more.

It is fascinating, but I have no idea how to introduce such complex techniques in a short blog post. If you do, please get started, I’ll be the first to read it!

So where does that leave us? Well, since we can’t easily increase the number of sweeps per second for these kernels, how about finding out some way to reduce the number of sweeps needed to solve the problem in the first place? This is what will be coming next. And it’s called SOR…
